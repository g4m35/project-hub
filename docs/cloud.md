# Your private cloud hub

Deploy one hub per owner. This alpha has no teams, shared workspaces, public signup, billing automation, or tenant isolation. Never remove the owner check to make it multi-user.

## 1. Prepare your own accounts and settings

Fork/download this repository and run `npm ci`, then:

```sh
npm run setup -- --cloud
```

This creates `.env.cloud` with a new random session secret and leaves existing configuration untouched. Edit the file privately. Required settings:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Your Neon Postgres connection string, using the database owner role |
| `NEON_AUTH_BASE_URL` | The Auth URL for the same Neon branch |
| `HUB_APP_ORIGIN` | Your final HTTPS hub origin, with no path (for example `https://your-hub.vercel.app`) |
| `HUB_OWNER_EMAIL` | The one email allowed to sign in |
| `HUB_SESSION_SECRET` | Generated by setup; keep it private and backed up |

`HUB_TEAM_ID` is needed for optional Vercel event setup. `HUB_GITHUB_TOKEN` and `HUB_VERCEL_TOKEN` are optional; you can connect them inside the authenticated hub instead. Never use the `VITE_` prefix for any secret. Changing the session secret makes existing encrypted provider credentials unreadable; reconnect them after an intentional rotation.

## 2. Configure Neon Auth and initialize storage

Enable Managed Better Auth on your Neon branch, enable email sign-up/sign-in in Settings → Better Auth (the [Email OTP APIs](https://neon.com/docs/auth/guides/plugins/email-otp) are built in), and add your exact `HUB_APP_ORIGIN` as a trusted domain. The app uses six-digit email codes and requires a verified owner email. Check [Neon's production checklist](https://neon.com/docs/auth/production-checklist), including your email sender configuration. Test delivery to the owner address before relying on this installation.

```sh
npm run cloud:check
npm run cloud:init
```

The checker validates configuration without printing secrets. Initialization creates the tables and an empty hub. Rerunning it preserves existing projects and subscriptions. It does not copy local files, projects or chats. Database RLS is enabled, public table access revoked, and all data access goes through the authenticated server using the database owner role.

## 3. Deploy to Vercel

Create a Vercel project from your fork with Node.js 24 or newer. `vercel.json` already sets the cloud build command. Add the required values above as **server environment variables for Production**; add optional provider values only if you use them. Do not upload `.env.cloud` or reuse production secrets in untrusted preview deployments.

Deploy, open the exact configured HTTPS address, request a code for `HUB_OWNER_EMAIL`, and sign in. Other email addresses are rejected. Open **Connections** to connect GitHub/Vercel, then **Add project**. The cloud picker reads GitHub repositories; it cannot scan folders on your Mac. Each cloud installation stores its own project list.

Troubleshooting: if sign-in emails do not arrive, check spam, the Neon email provider, OTP plugin and trusted domain. If the hub loads as a local app, verify the build command is `npm run build:cloud`. If cloud storage fails, rerun `cloud:check` and `cloud:init` with the correct branch. Never paste raw database errors or connection strings into public issues.

## 4. Optional deployment events

Vercel token-based polling works without webhooks. For direct events, set `HUB_TEAM_ID` to the team's `team_...` ID in both Vercel and `.env.cloud`. Connect a Vercel token in the hub or set `HUB_VERCEL_TOKEN`. Link at least one hub project to a Vercel project, then:

```sh
npm run cloud:events
```

This creates one webhook in your team, saves its encrypted signing secret, and imports up to 30 deployment records for each linked project. The webhook receives deployment events from the team, but the receiver accepts only linked projects from that exact team. New linked projects receive future events automatically; rerun this command to backfill their recent history. This alpha supports one Vercel team per hub.

Reruns reuse the webhook; its private recovery receipt is under `.data/integrations/`. An existing webhook without a recoverable secret stops setup instead of creating duplicates. Keep the receipt private and backed up. Requests require a valid HMAC signature over the raw body; out-of-order events cannot turn a completed build back into Building. To disconnect events, delete this hub's webhook in your Vercel account. The stored history is retained; remove the integration configuration only as part of a deliberate reset.

## 5. Optional Mac chat sync

On the Mac containing your Codex/T3 chats, keep a copy of this repository, run `npm ci`, and configure a private `.env.cloud` for your deployment. Then:

```sh
npm run sync:install
```

This explicitly authorizes this installation to read local chat metadata and upload it to **your configured HTTPS hub**. It uploads titles, IDs, app names, timestamps and activity only for chats matched to linked projects. Titles can contain personal information. Full transcripts, local paths, database credentials and provider tokens are not uploaded. Unmatched chats are excluded unless you run `npm run sync:install -- --include-unassigned`.

The installer creates a separate macOS LaunchAgent for each hub origin, syncing every 10 seconds while your Mac is awake and online. Its private config contains a narrow chat-sync credential. Data is stored under `~/Library/Application Support/Project Hub Open Source/Sync/`; the label is printed by `launchctl` and is namespaced by origin. Reinstall after upgrading Node or moving its executable.

```sh
npm run sync:stop
```

This unloads the job and disables its launch-at-login file while preserving private configuration for recovery. No chat databases are modified. Cloud deployments continue updating when the Mac sleeps; chat activity is marked offline after 45 seconds. Full conversations remain in Codex/T3.
